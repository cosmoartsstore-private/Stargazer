## 外部挙動の再監査

当初の整理には、内部リファクタリングではなく未承認の仕様変更が混在していました。差分を再分類し、次の対応を行いました。

- イベント写真・説明メモ、独自42日カレンダーを復元し、使用中イベントには削除ボタンを表示しない既存UIを維持した。
- 保存済み抽選を開いたときに、当選者だけでなく保存時の方式と抽選人数も復元する既存挙動を復元した。
- 要注意人物の登録経路、NGキャスト数、理由・メモを保持し、旧行を一律に手動登録へ変換しないmigrationへ戻した。
- `event_cast_present` と `header_templates` を削除しないmigrationへ戻した。過去の中間版で既に削除されたDBは後続migrationでschemaを再作成し、`event_cast_present` の欠損行だけは、旧表から移行済みの正 `casts.is_attend` から復元する。失われた `header_templates` の内容は推測しない。
- 削除済み・未解決の希望キャストは警告だけとし、抽選・マッチング・再実行・出力を制限しない最新決定へ合わせた。
- アプリ内Debug画面は、利用者の明示決定によりサイドバー入口と関連表示を含めて削除した。
- キャスト別NGと要注意人物の理由メモ、キャスト別名を承認済み機能として追加した。
- マッチング検証値、スコア表示の寿命、エラーダイアログの解除範囲を既存挙動へ戻した。
- 出欠、応募者削除、抽選、確定当選者選択は画面へ即時反映し、処理中の横断ロックを行わない既存UXへ戻した。DB失敗時だけ画面とDBの不一致を残さないため、最新操作を条件付きで戻す。
- 保存済み抽選名の当選人数、古い結果の確定当選区分、イベント名を空にしてフォーカスを外したときの挙動を既存仕様へ戻した。
- イベント切替失敗時に元の接続を自動復元する未承認変更を撤去した。

実データへ追加migrationを適用する前にアプリを終了し、利用者が管理する退避先へDataを複製して、複製元とバックアップのSHA-256が一致することを確認しました。個人環境のパス、実データのイベント名、件数は共有資料へ記録しません。

中間版で開かれた実データは個別に検査し、互換表のschemaと`casts.is_attend`へ移行済みの出席状態を後続migrationで復元する方針を確認しました。この結果を他のデータへ一般化せず、利用者が管理するバックアップを保持します。

### 2026-07-26 再監査追補

別モデルを含むHEAD対比を再実施し、追加で確認した外部挙動差分を次のとおり修正しました。

- キャスト改名時に完了済みマッチングを破棄せず、安定IDが一致する表示名とNG警告理由だけを更新する。
- 旧セッションに既存抽選結果がある場合は、V5 migrationとV6の追補で旧版と同じく現在結果として復元する。

- 要注意候補の閾値は複数桁を続けて入力でき、フォーカス移動時に保存する。候補表示は入力中の有効値へ追随する。

- 一覧中の1項目を読み取れない場合は、その項目だけを読み飛ばし、イベント・セッション一覧全体を失敗させない。
- アンインストールの保持範囲と、旧版入替時の `/UPDATE` 付与条件は開始時点の実装へ戻した。通常アンインストールは `Data/db`、`Data/logs`、旧WebView profileを削除するため、保持方針はSG-SPEC-026の未決定事項として残す。

旧DB、旧localStorage、旧WebView profileには移行先指定UIがありません。専用の検出警告、旧profile移動、混在ディレクトリの操作制限は明示承認のない外部挙動だったため撤去し、移行・保持方針はSG-SPEC-026の未決定事項へ戻しました。

### 2026-07-28 解消済み: イベント切替失敗時の接続復元

別イベントのDBを開けなかった場合は、切替前のイベントとセッション接続を開き直します。元の接続も復元できない場合は、React側のイベント名と表示キャッシュを破棄し、画面だけが旧イベントを参照する状態を残しません。イベント改名後の再接続に失敗した場合も同じ原則で、改名前の名前と接続を復元します。

### 削除・統合した重複

- Rust のDB初期化後の再接続、不要な共有DB走査、CASCADE対象の手動削除、単一SQLだけのtransaction、重複していたtransaction内部処理を削除した。
- 新規イベント・セッションの作成処理と既存ディレクトリを開く処理を分離した。有効名のディレクトリは既存DBの有無にかかわらず一覧へ表示し、現行DBがなければ初回open時に作成する。対応版より新しいschemaは変更せず拒否する。
- 新規イベント・セッションは一時ディレクトリ内でmigration、希望キャストID初期化、WAL checkpointを完了してから公開する。失敗時は一時ディレクトリだけを削除し、不完全な項目が一覧へ現れる状態を防いだ。
- 既存DBはmigration前後にschema versionとDB種別固有tableを検証する。未初期化のversion 0、共有・セッションの取り違え、対応外の将来versionを変更せず拒否する。
- 希望キャスト保存は `cast_ids` を必須とし、名前からIDを再補完する旧保存経路を廃止した。削除後に同名で登録された別キャストへ再接続しない。
- キャスト更新・改名・削除・出欠記録は安定IDをcommand境界に使用する。出欠履歴は日付×キャストの構造化1クエリへ統合し、`GROUP_CONCAT` と別集計SQLを削除した。
- キャスト一覧はキャスト・別名・連絡先・NGの固定4クエリ、応募者一覧は共有キャスト・応募者・希望・追加項目の固定4クエリで取得し、件数に比例するSQLを廃止した。子行のグループ化はDB repository共通の `groupRowsBy` に集約した。
- 応募者・抽選・キャスト・セッション条件の書込みキューを共通化した。接続を開き直して世代が変わっても同じSQLiteファイルへの書込みを呼出順に直列化し、成功済みキューは保持しない。
- イベント・セッションの最終使用位置を、localStorageの単一レコードを扱うAPIへ統合した。業務データはDBだけを正とする。
- Contextの未使用setter、再読込counter、重複close、起動時のセッション一覧二重取得、未使用barrel exportを削除した。
- 抽選画面の同型ハンドラー、マッチング状態の個別初期化、到達不能分岐、抽選結果の集計用中間関数を削除した。
- 抽選結果commandはFrontendで `applicant_id` を引き直さず X ID を渡し、Rust transaction内で現在セッションの応募者へ解決する。履歴保存時は現行 `lottery_results` を同じtransactionでコピーし、方式と人数もDB状態から導出して画面との二重管理を削除した。
- 空・重複 X ID の検査を `common/xIdUtils` へ集約した。新規取込と旧DBの既存行へ同じ規則を適用し、問題行が残る間はFrontendとBackendの両方で抽選・マッチングを停止する。
- 応募者の個別削除は `applicants.id` を使う専用transactionへ変更した。残りの不正行を全件検証し直さないため、複数の旧データを1件ずつ手動削除できる。
- 取込のカンマ区切り指定を `ColumnMapping.castInputType` へ統一し、別のoptions伝播と未使用設定を削除した。
- 応募者画面の要注意判定・NGキャスト集計・表示行生成を1回の走査へ統合し、一時的な自動要注意人物レコードを廃止した。
- NG画面のキャスト写し替え用配列、出欠serviceの中継関数、未使用の抽選結果削除APIを削除した。
- マッチング結果、テーブル配置、エラー、閲覧ロックを単一のContext状態へ統合した。画面を離れたときに消える既存挙動を保つため、スコア集計はマッチング画面のローカル状態に残した。

- 未使用のRepository API、出欠の未参照項目、単純な検証hook、保存件数専用型・関数を削除した。イベント写真・説明メモのmeta APIは既存機能として維持した。セッション更新commandは呼出時点のContextを必須引数にした。

### 整合性を修正した箇所

- 条件保存が失敗した場合、未保存の条件変更だけを戻す。抽選結果とマッチングの失効は、条件がDBへ保存された後に行う。
- 出席状態は画面へ即時反映し、保存失敗時だけ対象操作を戻す。全員出席・全員待機はキャストごとの複数commandではなく、単一SQLで更新する。
- キャストのプロフィール・写真はDB保存成功後に画面へ反映する。連絡先は既存どおり入力へ即時追随し、同じキャストへのDB書込みだけを呼出順に直列化する。
- イベント共有DBと取込セッションDBの失敗回復中は、古い楽観値から後続の業務処理を開始しない。回復後はDBの最終状態を再読込する。
- 新しい抽選と保存済み抽選の復元は、transaction完了まで現行結果とせず、名前付き保存とマッチングを開始しない。
- マッチング開始前にDBの条件・抽選結果・キャストと画面入力を照合し、Worker完了時にも接続、書込み、画面入力の各世代を再確認する。
- React StrictModeの開発時effect再実行でDB初期化を二重開始しない。

## データ分割の追加監査

メモリ使用量を抑えるためだけのFrontend DTO分割は確認されなかった。Worker入力は `UserBean[]` と `CastBean[]`、マッチング済みキャストは完全な `CastBean`、テーブル枠は完全な `UserBean` を保持している。`currentWinners` もID配列へ正規化せず、表示に必要な応募者オブジェクトを保持するため、現状はメモリ量より読解性を優先できている。

SQLiteの行型と画面オブジェクトの変換は、NULL、snake_case、複数tableの子行、イベント共有DBとセッションDBの寿命差を吸収するI/O境界である。巨大JOIN、JSON集約、Rust側の単一snapshot DTOへまとめても変換責務が移るだけで、行数と障害範囲が増えるため統合しない。

追加で統合できる可能性があるのは、同じマッチング結果を `userMap` と `tableSlots` の両方へ保持する箇所である。`tableSlots` を唯一の結果として応募者別・キャスト別表示を導出すれば60〜100行程度を削減できるが、アルゴリズム、安定IDの整合性、表示、出力を横断するため中リスクとする。

## 判断が必要な設計

以下は不具合として機械的に変更せず、製品方針と保守性を合わせて判断する。

### 1. 抽選条件の保存方式

現在はカウンターの連続操作へ即時追随するため、React stateを先に更新し、RepositoryでDB書込みを直列化しています。このため、表示値、最後の保存成功値、接続世代、操作順を個別に保持します。

単純化を優先する場合は、条件操作中だけ入力をロックし、DB保存成功後にstateを更新する方式へ変更できます。キューと複数ref、rollback処理の多くを削除できますが、各操作が数ミリ秒からDB応答完了まで待つUIになります。

### 2. ヘルプ画面の実画面プレビュー

`GuidePage.tsx` は 1,600 行を超え、実画面をサンプルContextで描画するため、Context変更のたびに追従が必要です。実画面との一致を優先するなら現状を維持します。保守量を優先するなら、静的な説明または画像へ変更し、サンプルContextを削除します。SG-SPEC-022と同じ判断です。

### 3. 旧形式データ互換

新schemaへのmigrationと旧localStorageから端末設定だけを引き継ぐ処理は維持しています。旧DB・旧業務localStorageを検出して移行する処理はなく、移行先と保持方法はSG-SPEC-026の未決定事項です。

### 4. 取込セッション履歴と保存済み抽選

通常UIは実質1セッションを扱い、一覧は最新セッションを選ぶ間だけ保持します。過去版が作成した旧セッションはディスク上に残りますが、選択UIはありません。保存済み抽選は履歴機能としてschemaと復元UIを持ちます。正式に履歴を残すか、今回限りの作業データへ限定するかで構造をさらに簡素化できます。SG-SPEC-015、SG-SPEC-027と同じ判断です。

### 5. 旧テンプレート用の取込項目

`ColumnMapping.nameColumn2` は現行UIから設定されず、旧テンプレート互換のテストだけが利用しています。旧テンプレートを入力契約として維持しない場合は削除できます。

### 6. イベント一覧のContext保持

`events` は実質的にイベント管理画面だけが利用します。画面ローカルへ移せばContextを縮小できますが、一覧再取得に失敗した場合に起動時取得済みの一覧を表示し続ける挙動を失います。失敗時に前回成功値を残す要件を維持する間は、Contextの表示キャッシュとして保持します。

### 7. DBファイル種別の識別子

共有DBとセッションDBは配置で役割を区別し、それぞれ同じ `stargazer.db` というファイル名と独立した `user_version` を使います。現在はmigration前にV1から存在する固有table、migration後に現行必須tableを検証し、誤配置したDBを変更せず拒否します。将来DBの手動import・移動を追加する場合は、table構成の推定ではなく `PRAGMA application_id` などの明示的な種別識別子を導入する余地があります。

### 8. 旧WebView2 profileの併存

開始時点の実装どおり、旧配置がWebView2 profileの形を持つ場合は起動時に削除します。通常アンインストールも旧profileを削除します。保持・移行へ変更する場合は、利用者データの優先規則と合わせて明示決定が必要です。

### 9. M003探索の運用既定値

M003は収束保証のないランダム探索を30秒で打ち切り、効率優先では最初の10秒だけ平均50点以上を求めます。処理手順と値の役割はWHYコメントへ明記しましたが、30秒・10秒・50点自体はアルゴリズムから導出される値ではありません。実運用の許容待機時間とマッチング品質を計測して変更するかは製品判断です。

### 10. 希望キャスト入力の表現

`UserBean` と Tauri payload は `casts[]` と `cast_ids[]` の並行配列を使い、希望方式は `applicant_extra.__preference_mode` に保存します。Rust境界では配列長、空名称とIDの不整合、希望方式、予約キーを検証しているため、現行動作の不整合は防いでいます。次回schemaを変更する場合は、希望を `{ name, id }[]` で表し、希望方式を専用columnへ移すと、表現不能な組合せとFrontend・Backend間の隠れた予約キーを削減できます。

## 構造上は大きいが、直ちに分割しない箇所

- `src-tauri/src/lib.rs`: migration、path、command、外部連携、テストが同居している。2,000行を超えるため外観上は大きいが、現在はschema変更が集中している。migrationとcommandの境界が安定した後に、`paths`、`migrations`、`commands`、`integrations`へ分割する。
- `LotteryPage.tsx`: 条件編集、抽選実行、履歴保存・復元を担当する。抽選条件の保存方式を決める前にhookへ移すと、現在の複雑さを別ファイルへ隠すだけになる。
- `NGUserManagementPage.tsx`: キャストNGと要注意人物は別ワークフローであり、今後どちらかが拡張される時点でパネル単位に分割する。現状の機械的分割は総情報量を減らさない。

## 現状維持が妥当な情報

- 接続世代とイベント・セッション識別子の確認は、切替前の非同期結果が切替後の画面を上書きしないために残す。
- 共有データ、セッションデータ、更新処理のloading状態は並行し得るため、単一booleanへ統合しない。
- 共有DB migration V2〜V7とセッションDB migration V2〜V6は、旧DBを段階的に開くための互換境界であり、重複コードとして削除しない。
- Rustが既存DBを検証してURIを返した後、Tauri SQL pluginが接続する前に外部からファイルを削除される競合は、通常UIの操作順では発生しない。完全に防ぐには参照処理もRust commandへ移す必要があるため、外部ファイル操作を正式に扱うまで構造を増やさない。
- 取込検証、抽選前チェック、マッチング計算などの純粋関数は、利用箇所が少なくても業務規則のテスト境界として残す。
- 小規模なfeature内helperは、複数workflowで共有されない限り共通Utilsへ移さない。

## 検証運用

- Frontendテストは純粋関数とmock repositoryが中心です。ブラウザE2EやReact画面操作テストはありません。
- Frontendテスト一式は約6秒、型検査とVite buildは約10〜20秒です。変更を数件まとめたcheckpointで実行してもフィードバックは十分速い状態です。
- Frontendは48ファイル・396テストで、coverageは statement 97.02%、branch 90.62%、function 100%、line 97.88%です。
- RustはSQLiteのmigration・transactionを含む46テストです。テスト本体は短時間ですが、Fドライブではincremental cacheのhard linkを利用できず、コンパイルに約1〜2分かかります。
- ルートの配布buildは最適化Rustコンパイルが支配的です。日常の小変更ごとではなく、配布・引渡しcheckpointで実行します。
- Viteは本番chunkが約701 kBのため警告を出します。Tauriではローカル読込であり、起動時間を計測して問題が確認されるまでは、画面を機械的に遅延分割しません。
